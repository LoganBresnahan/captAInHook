happened on the same day and they belong in one report because each is the
other's evidence: the docs sweep that closes the ADR's critical path, and six

## What is actually deployed — and what is not

**The live installation is `934f0cb` (2026-08-19 11:03). HEAD is `ffdace2`.**
Every commit since is undeployed, which means **the entire thread lane —
`thread-fields`, `mail-ask-wait`, `thread-aware-delivery`, `thread-canvas` —
has never run on the live bus.** It is built, green, and unshipped.

Two checkable consequences, both visible in the tree:

- **No live envelope carries `hops`.** All 15 envelopes on the ledger were
  appended by a build that had never heard of the field. The one `inReplyTo`
  on the ledger (`m-dogfood-hops-01-answer`) predates the lane it argued for.
- **The per-prompt tax measured over the last six days is the tax of the
  *old* build.** `mail-digest-ambient`, `handler.ok` `durMs`, lifetime:
  **n = 280, median 67.4 ms, p90 168.4 ms, max 420.6 ms**; restricted to
  2026-08-20 and after: **n = 92, median 74.3 ms, max 183.4 ms**. That is a
  clean six-day baseline for one unchanged binary — and it says *nothing*
  about what `thread-aware-delivery` costs, because that code is not running.
  The measurement to take after the next `/deploy` is the same one, and the
  question it answers is whether reading a thread at plan time is free.

Worth saying plainly because it is the trap this report exists to avoid: a
green suite is not a field observation. Four slices of the thread lane are
recorded as landed and are, but nothing in `doc/` claimed they were live, and
they are not.

## The bus went quiet on 2026-08-19, and kept delivering anyway

Last append: `2026-08-19T16:28:40Z`. Since then: **zero** `mail.append`.

Today, 2026-08-25, the same ledger produced **11 `mail.deliver` records across
6 windows** — every one at the `ambient` seam (UserPromptSubmit),
`vehicle: inject`, and every one handing over the *same* six-day-old
envelopes. The shape is exact and it
repeats per window:

| window | first pickup | second pickup |
|---|---|---|
| `26576ab2` | 4 envelopes (`dogfood-002`, `live-demo-002`, `review-1ee7218-reply`, `statusline-demo-02`) | 5 envelopes (`m-dogfood-hops-01-answer`, `dogfood-001`, `live-demo-001`, `live-demo-003`, `statusline-live-01`) |
| `deba30eb` | the same 4 | — |
| `f1f7709f` | the same 4 | the same 5 |
| `e544cb9e` | the same 4 | the same 5 |
| `e92e87db` | the same 4 | the same 5 |
| `30fdbb20` | the same 4 | the same 5 |

The split is the digest's own: the 4 urgent-class envelopes go first and the
5 ambient ones are held for the next delivery opportunity — which is why
`deba30eb`, a window that took one prompt and stopped, only ever saw the
urgent half.

**Finding 1 — the retained backlog is re-delivered in full to every new
window, and this is the human side of `turn-pickup-bound`.** A new session
gets a fresh cursor at the anchor, so everything still within `ttlDeliveries`
is unread *to it*. That is correct by the cursor rule and it is exactly what
ADR-0017's deferred `turn-pickup-bound` row describes for a robot's ephemeral
mailbox — "a first pickup on a role's new sessionless mailbox delivers the
whole retained backlog, not the nudged envelope." The row deferred it on the
grounds that it "bites only when the reference integration is run in earnest."
It also bites, quietly and every day, on a human role with a lot of windows.
It costs no tokens on the human channel (the digest is an injection, not a
turn), which is why it went unnoticed — but the ordering is now on the record:
**the bound is a bus property, not a watcher property.**

**Finding 2 — TTL expiry is counted per cursor, so one envelope expired ten
times.** `dogfood-003` (`ttlDeliveries: 1`, offset 444) has **10 `mail.expire`
rows**, four of them today, each from a different mailbox reaching its own
`seenAt: 1`. Nothing is wrong: TTL belongs to a cursor's reading, exactly as
"pending belongs to a CURSOR and not to a role" (2026-08-17). But the trail
reads as though one envelope died repeatedly, and anyone counting expiries to
answer "how much mail aged out" will over-count by the number of windows. A
row that is right per cursor and misleading in aggregate is worth a note
before someone builds a metric on it.

## The sweep: what mechanical checking found

Phase 7's bar was "every symbol named exists." Run as a mechanical check
against the ground-truth tables of `doc/flow/mailbox-bus.md`, ADR-0016,
ADR-0017 and ADR-0018:

**Names never drifted.** All 251 backticked identifiers in ADR-0017's Ground
truth and all 383 in the flow doc's resolve to something in `dotnet/`,
`web/src/`, `web/e2e/` or `examples/`. Every file path named exists (the four
that do not are `~/.captainHook/` runtime files, correctly so).

**Numbers drifted, twelve times, and eleven of them the same way.** Eleven
stale counts were *low* — taken when the row was written and never re-measured
as cases were added. One was *high*, and it is the more interesting kind:
`ApiHandlersWriteTests` claims 17 where the runner reports 16, so a case was
removed and the row was not:

| where | claim | measured |
|---|---|---|
| flow `mailbox-bus.md`, ADR-0018 | `MailInstanceRegistrationTests` 13 | **14** |
| ADR-0018 | `MailAddressTests` 17 | **21** (17 + two length theories that expand to 4) |
| ADR-0018 | `WatcherDeadMailboxTests.cs` 19 | **21** |
| ADR-0016 | `MailEnvelopeTests.cs` 115 | **147** |
| ADR-0016 | `MailStoreTests.cs` 46 | **52** |
| ADR-0016 | `mailCanvas.test.ts` 39 against 16 goldens | **48** against **17** |
| ADR-0017 | `RoleKindsTests.cs` 18 | **20** |
| ADR-0017 | `MailWatchTests.cs` 20 | **24** |
| ADR-0017 | `MailNudgeEventTests.cs` 11 | **13** |
| ADR-0017 | `MailStatusTests.cs` 30 | **36** |
| ADR-0011 | `ApiHandlersWriteTests` 17 | **16** |

Plus three bare `MailEnvelopeTests` citations that name a FILE, not a class —
there is no such class, and the flow doc's own convention is per file. Now
written `MailEnvelopeTests.cs`.

**Finding 3 — the flow doc's warning about counts is right, and the check it
describes should be automated.** `doc/flow/mailbox-bus.md`'s Ground truth
preamble already says these numbers have drifted three times and gives the two
commands that reproduce them. They drifted eleven more times anyway, because a
reproduction command nobody runs is a comment. The check is cheap — `dotnet
test --list-tests` piped to a per-class count, `node --test <file>`'s `ℹ tests`
line, both already in the preamble — and its failure mode is a one-line diff,
not a judgment call. **Candidate `/shipshape` gate**, and unlike most doc
checks it cannot produce a false positive: either the runner reports N or it
does not. Names would still need eyes; numbers would not.

The direction of the drift is the argument for automating it. Eleven low
counts means the tables mostly under-report coverage — the least alarming way
to be wrong, and therefore the way that survives longest unnoticed. The one
high count is the case a human reader can never catch by feel: a number that
went *down* is a test that stopped existing.

## Watchlist

- **Deploy, then re-measure the digest.** The thread lane's per-prompt cost is
  unknown; the pre-lane baseline (median 74.3 ms, n = 92) is recorded above so
  the comparison is one command after the next `/deploy`.
- **`turn-pickup-bound` is a bus bound, not a watcher bound** (finding 1). Its
  deferral reasoning should be re-read with the human side in view.
- **Per-cursor expiry counting** (finding 2) — before anything aggregates
  `mail.expire`.
- **17 of 30 cursors dead** — the number ADR-0018's `reaper-payloads` inherits.
- **A count gate in `/shipshape`** (finding 3).
- Still unobserved, and still deliberately so: N2 idle-exit, presence false
  negatives on a `mixed` role, recurrence against `perRoleHour`, and whether
  `mail ask --wait` is wanted by anyone in practice.
