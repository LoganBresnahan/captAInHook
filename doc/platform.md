# Platform envelope — OS facts the design leans on

Environmental constraints, not decisions: things the kernel or OS imposes that
are true regardless of what we choose. ADRs record what we *chose* under these
facts (and cite them); flow docs record what the *code* does; this file is the
re-audit checklist when a fact changes or a new OS becomes a target. Each entry
names what leans on it, so nothing here is trivia.

Verification status: **Linux/WSL2 is the lived-in target** — facts there are
exercised by the test suite or observed live. **macOS is a committed target**
(ADR-0012) pending the `/proc`→`sysctl` port; its entries are researched, not
yet exercised — promote them to verified the day a real run touches them.
**Windows-native is out of scope** (ADR-0012): WSL2 is the Windows path.
Windows entries below are kept as WSL2/AF_UNIX context, not a portability goal.

## Unix domain sockets

| Fact | Detail | What leans on it |
| --- | --- | --- |
| `sun_path` caps at ~108 bytes | Linux 108 incl. NUL; macOS 104; Windows AF_UNIX also ~108. Hit live 2026-07-05: a scratchpad-length socket path aborted with `ArgumentOutOfRangeException` before bind. | ADR-0004 decision 3 (as amended 2026-07-05): runtime files under `$XDG_RUNTIME_DIR/captainHook/` when set, else `~/.captainHook/`, plus a clear-error guard at resolve time — `Core/Rendezvous.cs`. |
| Path choice must be a pure function of env | The shim is per-invocation with no memory and no side channel to the daemon; both sides must *compute* the identical path. Probe-until-fits or any stateful negotiation is unsound by construction. | The whole filesystem rendezvous (ADR-0004 decisions 2–3). |
| AF_UNIX exists on Windows 10 1803+ | .NET's `UnixDomainSocketEndPoint` supports it; same length cap. Named pipes are the Windows-native alternative if AF_UNIX gaps appear. | Keeps the wire design portable in principle; see the Windows caveat below for what is *not* portable. |
| `connect()` succeeding ≠ peer healthy | A listening socket's backlog accepts connects even if the accept loop is wedged or draining. | ADR-0004 decision 2's shim-side deadline spanning connect + request + response. |

## Loopback TCP & managed `HttpListener` (management API)

The management API (ADR-0007) rides the *managed* `HttpListener` — on Unix
there is no http.sys; the BCL ships its own socket-level implementation, "the
least-loved corner of the BCL" (ADR-0007 N5). Bind-boundary facts probed
2026-07-07/08 (Linux/WSL2, .NET 10) for the singleton-port cutover; the API's
own mechanics live in [flow/management-api.md](flow/management-api.md):

| Fact | Detail | What leans on it |
| --- | --- | --- |
| An active listener blocks a second bind — no co-bind | Cross-process: `HttpListenerException` "Address already in use" (kernel EADDRINUSE; SO_REUSEPORT is not set). In-process: `HttpListenerException` "conflicts with an existing registration" from the managed prefix table, before any syscall. | ADR-0007 d2's port-is-a-singleton premise: a successor *cannot* steal, only wait for the incumbent's drain-start release. `ApiHost` retry loop catches `HttpListenerException`; pinned by `ApiRetryBindTests.StartRetrying_NeverStealsAnActivelyHeldPort`. |
| TIME_WAIT residue does NOT block a **.NET→.NET** rebind | Served-and-closed connections leave `127.0.0.1:<port>` TIME_WAIT entries (60s on Linux). The mechanism is NOT `HttpListener` (its managed listener sets no socket options — verified in dotnet/runtime source): the **.NET Unix PAL sets SO_REUSEADDR unconditionally on every TCP bind** (`SystemNative_Bind`, pal_networking.c). And Linux only honors it pairwise (kernel-probed 2026-07-07): a bind over server-close TIME_WAIT needs reuse on BOTH the new socket AND the listener that created the residue; client-close residue never blocks. Both daemons are .NET ⇒ both halves hold ⇒ rebind in ms (probed: 17ms through live worst-case residue). | Handoff latency = release→bind, not release→2·MSL — but only across .NET incumbents. A **non-.NET** prior occupant of the port that closed server-side can block the bind up to ~60s; the retry loop's slow cadence absorbs exactly that (warn, never fatal). Pinned by `ApiRetryBindTests.Rebind_ThroughTimeWaitResidue_IsImmediate` — which guards the **PAL default**: if it ever reds, hunt in Socket/PAL, not `HttpListener`. |
| Loopback bind is unprivileged | No urlacl/reservation step on Unix (that is http.sys ceremony); any user binds ≥1024. Ports <1024 still need root — the failure surfaces as the same bind exception, i.e. warn + slow retry, never fatal. | The API existing with zero install-time OS setup (ADR-0007 d1); `ApiHost.ResolvePort` accepting any 1..65535 without a privilege check. |
| Managed `HttpListener` teardown BLOCKS behind a wedged write; `Close()` terminates nothing | Probed 2026-07-08 (idle-exit-defer's adversarial verify): with a server write parked on a zero-window client (a subscriber that stopped reading), `HttpListener.Stop()`, `Close()`, and `HttpListenerResponse.Abort()` all **block indefinitely** — there is no per-connection force-close on Linux. With HEALTHY clients, `Stop()`/`Close()` return promptly but terminate **no** in-flight streams (a token-ignoring writer keeps streaming through both). And the **listen port frees the instant `Stop()` begins**, even while the call is blocked. | `ApiHost.Stop()`/`Dispose()` run listener teardown on a bounded background task — a synchronous call would turn one stalled SSE subscriber into an unkillable daemon (drain wedges before `daemon.drainStart`; the version lock never releases; SIGTERM stays claimed by the drain registration) — and stream termination is owned by the `_stop` token + each writer's own `resp.Close()`, never the listener. Pinned by `ApiSseHttpTests.Stop_IsBounded_EvenWithAWriterWedgedOnAZeroWindowClient`; the port-frees-at-Stop-start fact is what keeps the N1 handoff fast even off a wedged incumbent. |
| The managed listener PREFIX-MATCHES on the Host header | With prefix `http://127.0.0.1:<port>/`, only a request whose `Host` is exactly `127.0.0.1:<port>` reaches user code. A foreign Host (a DNS-rebind page naming `attacker.example`) or even `localhost:<port>` gets a **404 from the listener itself** before any handler; an empty Host → 400. Probed 2026-07-07. And `HttpListenerRequest.UserHostName` returns the matched PREFIX authority for dispatched requests, not the raw client Host. | ADR-0007 decision 6's rebind defense: the listener refuses a foreign Host first, so `ApiAuthGate`'s own Host→403 check is portable defense-in-depth (unit-tested directly, since real HTTP can't reach it here); and the API answers `127.0.0.1` only — supporting a `localhost` origin would need a second prefix (deferred). `ApiAuthHttpTests.ForeignHost_RefusedByTheListener` pins the 404-before-gate behavior. |

## Browser engines (the management GUI)

The GUI is served same-origin by the daemon and consumes the trail over `fetch`
+ `ReadableStream` (not `EventSource` — it must send the bearer). Engine facts
that shaped it, probed 2026-08-16 (Firefox 151 / Chromium 141 via Playwright,
against the live daemon):

| Fact | Detail | What leans on it |
| --- | --- | --- |
| **Firefox serializes concurrent requests to the SAME URL** behind its HTTP-cache entry lock, and holds the lock for the whole response body | While one `GET /api/v1/events` streams, a second plain `fetch("/api/v1/events")` from the same page **never receives headers** — measured: neither of two new same-URL streams got headers in 2.5 s beside the app's own; the same two with `cache: "no-store"` (or distinct URLs) got them in 4–5 ms. Server-side `Cache-Control: no-store` does not lift it (the lock is taken before the response is classified). Chromium served all three concurrently. | `apiFetch` (`web/src/auth.ts`) sends `cache: "no-store"` on every call — the Mail view's second subscription, and any reconnect racing the socket it replaces, depend on it. Pinned by `stream-health.spec.ts` "two subscriptions on one URL" under the `firefox` project; the dogfood symptom it explains (a badge live, `openStreams` at 1, a view that never filled) is in `doc/dogfood/`. |
| Streamed-fetch chunk delivery itself is prompt in both engines | Page-first-then-real-dispatch rendered rows within ms in headless Chromium **and** Firefox against the live 2 MB trail; the WSL2 localhost relay (`curl.exe` from Windows) forwarded frames 50–200 ms after dispatch. Neither is where the 2026-08-16 finding lived. | Why the fix is `no-store` + a stall watchdog, not a transport change (WebSocket buys nothing here: the browser `WebSocket` cannot send headers either, and the GUI never writes on the bus). |
| Playwright Firefox does not hand a rerouted (`route.continue({url})`) streaming response to the page headers-first | The `fetch` never resolves until the rerouted body completes — a state that is "headers arrived, body never will" cannot be staged there. | `stream-health.spec.ts`'s STARVED spec runs in Chromium and `test.skip`s Firefox with this reason; the verdict itself is pure and pinned in `streamHealth.test.ts`. |
| Playwright clicks the bounding-box centre; Firefox's SVG hit-test at that point can find the lane, not the glyph | A `<g role=button>` that also holds a thin drop-line has a bbox centre on bare lane between line and card. A user clicks the card. | `mail.spec.ts` clicks `.glyph-body`, not the group. |

## Runtime directories

| Fact | Detail | What leans on it |
| --- | --- | --- |
| `XDG_RUNTIME_DIR` is Linux/systemd | Set by pam_systemd to `/run/user/<uid>`: short by construction, per-user `0700`, tmpfs, wiped at logout. Present on systemd-enabled WSL2. Essentially never set on macOS or Windows. | The socket/lock/pid directory choice. "Is it set?" is itself the deterministic branch — unset simply means the `~/.captainHook/` fallback, which is short on macOS (`/Users/<name>`) and Windows (`C:\Users\<name>`). |
| tmpfs wipe at logout is acceptable | Lock/pid files are tiny, version-bounded, and meaningful only while a daemon lives; a daemon rarely outlives the login session that spawned it (systemd may kill user processes at logout anyway — `KillUserProcesses`/linger). | ADR-0004 decision 4's cleanup story; `doctor` reaps whatever survives. |
| .NET's `File.AppendAllText` does NOT open O_APPEND | strace on .NET 10/Linux (probed 2026-07-08, during ADR-0007 sse-trail-tail's adversarial verify): `openat(O_WRONLY\|O_CREAT)` — **no O_APPEND** — then `pwrite64` at offsets cached at open. Two processes appending in the same sub-ms window compute the same base offset and can OVERWRITE each other's lines. | ⚠ Contradicts `WireJsonl.Append`'s "O_APPEND keeps concurrent writers whole" comment and ADR-0004 N3's two-emitters-one-file integrity story: shim + daemon CAN clobber under concurrent append. The SSE tailer (ADR-0007 d5) is schema-blind and ships whatever bytes exist — reader unaffected; the fix is EMITTER-side (true O_APPEND open), tracked in doc/scratch.md. |
| `CreateDirectory(dir, mode)` can't retighten a pre-existing dir; secrets need create-time modes | The `UnixFileMode` arg applies only when the dir/file is CREATED — on a pre-existing one it is silently ignored. And `WireJsonl.Append` creates `~/.captainHook` (via `logs/`) at the **umask default (0755)** on the first hook, typically before any daemon. So the runtime dir is only reliably private once `DaemonRendezvous.TryAcquire` **explicitly** `SetUnixFileMode`s it to 0700, and the `api.json` token is created 0600 **at birth** (`FileStream` `UnixCreateMode`, never write-then-chmod) so it is never world-readable even in a window — the trust root both ADR-0004 d3 and ADR-0007 d6 assert. Probed live 2026-07-07. | The 0700-dir + 0600-token trust root; `LockBindTests.Acquire_Tightens_APreExisting0755RuntimeDir`, `ApiDiscoveryTests.Write_Is0600AtBirth`. **Residual (pre-existing, ADR-0004 logging):** the JSONL trail file is created 0644 and, in the window before a daemon tightens the dir (or in pure-collapsed/no-daemon runs), sits in a 0755 dir — a co-located user could read it. The token is unaffected (always 0600); closing the trail window means the shim/`WireJsonl` creating the dir 0700 + the trail file 0600, tracked as a logging-layer follow-up. |
| File mtime resolution is fine-grained on normal local filesystems, coarse on some | On ext4/APFS/NTFS/btrfs, `LastWriteTimeUtc` carries ns/100ns precision (probed 2026-07-08: 0 tick-collisions in 2000 rapid successive writes). FAT/CIFS/older-ext3 quantize to 1–2s. | `ReloadingPolicy`'s policy hot-reload stat-gate keys on `(mtime,size)` (ADR-0006 d6); on a fine-grained FS it reliably notices every `dispatch.json` change, so a `put-policy-write` PUT is effective on the next dispatch. On a coarse-mtime store a **same-length** change within one granule can be missed — a hardening follow-up (inode/ctime discriminator, NOT a hot-path content hash), tracked in doc/scratch.md § Policy hot-reload robustness. |

## File locking & process lifecycle

| Fact | Detail | What leans on it |
| --- | --- | --- |
| POSIX exclusive lock released on any death | An `O_EXCL`-style held lock (`FileShare.None` handle) is released by the kernel on process exit, crash included — no cleanup code required for correctness. | ADR-0004 decision 3: kernel-settled spawn races; "lock files are never unlinked." |
| Deleting a held lock file breaks mutual exclusion | A second process can lock a *fresh inode* at the same path while the first still holds the old one. POSIX-specific footgun. | The "no component ever unlinks a lock file, `doctor` included" rule. |
| Windows lock semantics differ | `FileShare.None` gives exclusivity, but the unlink-while-held / fresh-inode dance is POSIX-flavored; Windows would want a named mutex (or rely on its default can't-delete-open-files behavior — which then breaks the *socket* unlink step instead). | ⚠ The rendezvous mechanics (lock + stale-socket unlink + bind) are **not** Windows-portable as designed. Windows-proper support = its own audit + ADR-0004 amendment. Parked: WSL2 is the Windows story today, and it is Linux for these purposes. |
| PIDs are reused | A recorded pid may name an unrelated process by reap time. | `doctor`'s liveness *plus* binary-identity check before SIGTERM (pharos ADR-030 lineage). |
| `/bin/sh` exists; `sh -c 'exec … &'` detaches | POSIX shell as OS facility (not a dependency): the `&` subshell + `exec` + parent-exit reparents the child to init with /dev/null stdio. .NET alone cannot redirect a child to /dev/null or setsid portably. | `DaemonSpawner.Detached` — the shim's spawn-on-fallback (ADR-0004 decision 2). |
| `dotnet foo.dll` makes `Environment.ProcessPath` the MUXER | Under framework-dependent `dotnet <dll>` invocation, ProcessPath is `/…/dotnet`, not the app — a self-respawn would exec `dotnet --daemon` (a CLI error). Only the apphost executable yields the app's own path. | `DaemonSpawner`'s muxer guard (refuses + `shim.spawnFailed`); the `/deploy` skill's apphost requirement (doc/flow/live-deployment.md). |
| **No BCL append path sets `O_APPEND`** | `File.AppendAllText`, `new FileStream(FileMode.Append)`, and `File.OpenHandle(FileMode.Append)` all `openat(O_WRONLY\|O_CREAT\|O_CLOEXEC)` and then `pwrite` at an offset resolved AT OPEN — strace-probed on .NET 10 / linux-x64, 2026-08-11. Concurrent appenders therefore compute the same end offset and overwrite each other: at 8 writers × 250 lines the old emitter body lost **~1100 of 2000 lines** (55%) and fused others. There is no managed escape; `O_APPEND` requires `open(2)`. | Why BOTH trail emitters P/Invoke libc `open`/`write` instead (`captainHookWire/PosixTrail.cs` and its F# mirror in `Logging.fs`) — ADR-0004 N3's convergence story assumes the shim and daemon can append the same file. Pinned by `TrailAppendTests`. |
| `open(2)` is variadic, and Apple arm64 passes variadic args differently | `open(const char*, int, ...)`: on Apple arm64 the variadic tail uses a different calling convention than fixed parameters, so a 3-arg P/Invoke declaring `mode` as fixed would place it wrongly. Passing NO variadic argument is well-defined on every target. | Why `PosixTrail` creates the file through the BCL and then opens with the two-argument form (no `O_CREAT`) — the macOS target is code-complete but unproven (ADR-0012 N2), so its ABI edges are avoided rather than trusted. |
| `open(2)` flag VALUES differ per OS | `O_APPEND` is `0x400` on Linux, `0x0008` on macOS; `O_CLOEXEC` is `0x80000` on Linux, `0x1000000` on macOS. Only `O_WRONLY` (1) agrees. | The per-OS constants in both `PosixTrail` implementations — a single "portable" constant would silently open with the wrong flags on the second target. |
| .NET cannot preemptively kill user code | No `Thread.Abort`; a wedged, token-ignoring handler's task can only be abandoned, not destroyed (the honest cost of not being on the BEAM). | ADR-0004 decision 5's abandon-and-respawn + leak accounting; wedges count toward escalation. |

## Process groups (exec-handler kill discipline)

| Fact | Detail | What leans on it |
| --- | --- | --- |
| `ProcessStartInfo.CreateNewProcessGroup` is Windows-only | Present in the .NET 10 surface but throws `PlatformNotSupportedException` on Unix (probed 2026-07-12, SDK 10.0.301); .NET exposes no setpgid seam around its fork/exec. | Why the group is made by a *spawn wrapper* instead of a start-info flag (ADR-0010 d6 kill-discipline amendment). |
| No managed runtime exposes the fork→exec window, and FFI cannot substitute | `setsid(2)`/`prctl(PR_SET_PDEATHSIG)` must run **inside the child** between fork and exec; a P/Invoke sets the attribute on the *calling* process (the daemon). True of .NET, BEAM, and the JVM alike (ADR-0013 Findings 3–6, probed 2026-07-27). | Why the fix is a wrapper EXECUTABLE, not a library or a P/Invoke — ADR-0014's "minimal ownable form". |
| A wrapper that execs in place preserves the pid | Both `setsid(1)` and `bosun` `exec` the payload over themselves, so the `Process` handle .NET got from spawn IS the payload, and pgid == sid == pid. Verified for bosun against a real kernel (its `test/smoke.sh`); pinned here by `SpawnPrefixTests` through a contract-enforcing stand-in. | The whole identity story downstream: `Process.Id` as both kill target and pgid, `ChildRecords` pid identity, the liveness probes. |
| `bosun` provides `setsid()` on macOS, where `setsid(1)` does not exist | The *syscall* is present on macOS — only util-linux's binary is missing. bosun (~130 lines of Zig, MIT, <https://github.com/LoganBresnahan/bosun>) calls it directly; Linux builds are musl-static (28 KB, run in `FROM scratch`), macOS builds link libSystem. Fetched at deploy time by pinned tag + `SHA256SUMS`, never "latest". | ADR-0014 d1–d4: the co-located first rung of `ProcessGroup.Resolve`, staged by `/deploy` as the fourth artifact. Native ⇒ no MVID ⇒ invisible to content identity, exactly like `captainShim`. |
| `setsid(1)` execs IN PLACE when the caller is not a group leader | util-linux setsid forks only if it already leads a group; a freshly forked child never does, so `setsid <cmd>` keeps the pid (`Process.Id` IS the payload) and yields pgid == sid == pid. Grandchildren inherit the group. Probed 2026-07-12: pid preserved; `kill(-pid, TERM)` took a backgrounded grandchild; a `trap '' TERM` group survived TERM and died to `kill(-pid, KILL)`. | `ExecHandler`'s spawn prefix + `ProcessGroup.TermThenKillAsync` (libc `kill(2)` P/Invoke, the Doctor.cs precedent); `KillDisciplineTests`. |
| Ignored signal dispositions survive fork+exec | `trap '' TERM` in a payload script leaves SIG_IGN set in every descendant — a whole group can shrug off SIGTERM. | Why TERM→grace→**SIGKILL** escalation exists (and is trailed: second `exec.kill` line, `how=kill`). |
| `Process.Kill(entireProcessTree)` walks /proc descendants only | A grandchild that reparents to init (double-fork daemonizer) leaves the walkable tree and survives; a process group keeps it reachable. | The degrade path when NO spawn wrapper resolves (flagged per-spawn: `exec.spawn` `spawner=none` + `pgroup=false`) — group kill is the primary for exactly this gap. |
| macOS ships NO `setsid(1)` | The utility is util-linux; stock macOS lacks it (installable via brew's util-linux). The syscall exists — only the wrapper binary is missing. | The reason rung 2 cannot be the only rung. **The ⚠ this row carried is RETIRED (2026-08-11, ADR-0014):** a staged deploy resolves `bosun` first, so macOS gets real process groups. The degrade survives only where NEITHER wrapper is present — a dev tree on a stock Mac, or a container image with no util-linux and no staged bosun — and stays loud per spawn (`spawner=none` + `pgroup=false`). |
| Signal-0 liveness counts zombies as alive | `kill(pid, 0)` succeeds on an exited-but-unreaped child; `kill(-pgid, 0)` likewise while any member (zombie included) remains. | `ProcessGroup.IsAlive` prefers `Process.HasExited` for the leader (the runtime reaps its own children) and probes the GROUP once the leader is gone — a leader-only check reads `sleep 300 & exit 0` as dead and orphans the grandchild; tests treat /proc state `Z` as dead. |
| A pgid persists while any member lives | The group survives its leader's exit (orphaned process group); the pgid cannot be recycled until every member is dead and reaped. | Group-probe liveness after leader exit; the accepted residual (a stray signal needs a full pid-space wrap inside the ≤3s kill window). |

## Wall-clock steps (why invariant 2 is not theoretical)

| Fact | Detail | What leans on it |
| --- | --- | --- |
| **WSL2's wall clock steps by tens of seconds, in both directions** | Measured 2026-08-11 by sampling `CLOCK_REALTIME` against the monotonic clock every 100ms: a **+86.4s** step while the monotonic clock advanced 101ms, and a **−86.7s** step back a minute later; a start-to-ready measurement spanning one read as **negative** elapsed time. Frequency here: roughly one step per 10–15 sequential daemon starts, on an otherwise idle machine. **Mechanism (maintainer's machine, 2026-08-11):** this box dual-boots Windows and Linux under GRUB, so the two OSes disagree about the RTC and Windows re-syncs its clock against time.windows.com to correct the accumulated drift; WSL2's guest clock follows the host through Hyper-V time sync, and each correction lands in the guest as a step. Nothing in the workload provokes it — it is a property of the machine, and it will keep happening. | House **invariant 2** — every deadline, interval, and restart window uses a monotonic source. The engine already obeys it (`Stopwatch` / `TickCount64` throughout; `DateTime.UtcNow` appears only in log *timestamps* and the opt-in `ColdStartProbe` boot delta). The e2e/dev-loop harness did NOT: `web/e2e/daemon.ts`'s readiness deadline was `Date.now()`-based, so a forward step "expired" a 40s deadline against a daemon that was perfectly healthy — the whole of the suite's long-standing readiness flake, previously (and wrongly) blamed on a thread-pool warm stall. Now `performance.now()`. |
| A stalled-looking process with **no syscalls at all** in the window is the signature | strace of a "stalled" daemon showed an 86.30s gap between consecutive syscalls with every thread parked in `futex_do_wait` and no CPU burn — i.e. no work was skipped, no time actually passed. Wall-clock timestamps in a log (`Actors.Log`, `WireJsonl`) inherit the step, so a trail can show an 86s gap between two adjacent `actor.spawn` lines that were microseconds apart. | Reading the trail's `ts` as a *duration* is unsound on this platform; `durMs` fields (Stopwatch-derived) are the trustworthy ones. Anything asserting "X took N seconds" from two timestamps must be understood as display-only. |
| The invariant predates the measurement | `Supervision.fs`'s restart-window math already carried "wall clock can step under NTP corrections or **dual-boot RTC**" as its reason for taking a monotonic source — written before this was ever observed. The 2026-08-11 measurement is that comment being proven right on the maintainer's own machine, and the only place the rule had leaked was the TypeScript test harness. | Why invariant 2 covers *every* layer that computes a deadline, test code included — a dev-loop harness that measures with the wall clock will misreport a healthy system as a broken one, and did for a month. |

## The Stop block shape (the harness's turn-end contract)

The environment *imposes* this one: Claude Code decides what a hook may say at
turn end, and it says it differently there than anywhere else. Read off the
**shipped host's own schemas** — Claude Code **2.1.119**, probed 2026-08-13 —
because the published docs describe a different shape (last row).

| Fact | Detail | What leans on it |
| --- | --- | --- |
| `hookSpecificOutput` is a **union with no `Stop` member** | The host parses it as a union keyed on `hookEventName`, and exactly 17 variants exist — `PreToolUse`, `UserPromptSubmit`, `PostToolUse`, `SessionStart`, `Setup`, `SubagentStart`, `PermissionRequest`, `Elicitation`, … — with **`Stop` and `SubagentStop` absent**. The `permissionDecision` shape every other event takes therefore does not merely get ignored at turn end: it fails the union parse and the DECISION evaporates. The failure itself is not quite zero-signal — the host surfaces a verbose-only `hook_non_blocking_error` and, at Stop specifically, a "Stop hook error occurred" notification — but the block is lost either way, and a turn-end block that does not block is the hazard. | `ClaudeHookJsonAdapter.DecidesAtTopLevel` (ADR-0016 d5's reconcile seam). This is the "a wrong Stop block shape ships silently" hazard, stated concretely. |
| Stop blocks via the **top-level `decision`/`reason` pair** | `decision: "approve" \| "block"`. `block` builds a *blocking error* whose text is `reason \|\| "Blocked by hook"`; the host appends it to the conversation as a message, which is what "prevents Claude from stopping" actually means — the turn continues carrying the reason. Exit code 2 does the same with stderr as the text. | The digest's reconcile vehicle: the rendered digest IS the `reason`, so the recipient reads its mail as the continuation prompt. |
| The vocabulary is **two words, and a third is discarded** | The top-level enum is `approve\|block` only; any other word fails the host's schema validation and the whole output is dropped as a non-blocking hook error (an internal `Unknown hook decision type` throw exists but sits behind the enum — dead code; even the runner's throws are caught and surface as `hook_non_blocking_error`, never a crash). Our `Verdict` carries a third value (`ask`) that has no meaning at turn end anyway. | Why the adapter degrades `ask` on Stop to noop instead of passing it through — house rule: never send a harness something it cannot represent. |
| A **mismatched `hookEventName` is an error, not ignored** | `if (expected && out.hookSpecificOutput.hookEventName !== expected) throw` — the host compares the name we echo against the event it dispatched; the throw is caught by the hook runner and surfaces as a `hook_non_blocking_error`, discarding the output. An off-case name (`stop` vs `Stop`) loses the effect, not a near-miss. | `Harness.Canon` PascalCasing **single-word** events. It used to pass `stop` through untouched — the install template writes `hook {event-kebab}`, so that is exactly what arrives live. |
| ⚠ **`replaceOutput` does not exist in the shipped host** | The `PostToolUse` union member accepts `additionalContext`/`updatedMCPToolOutput` only; the key `replaceOutput` appears NOWHERE in the 2.1.119 binary, and the schema's unknown-key strip means an `Effect.Replace` parses *successfully* and is discarded with no error of any kind — quieter than the Stop failure. Pre-existing (not introduced by the Stop seam), same disease. | The spec's `PostToolUse: ["inject","replace"]` advertises a capability 2.1.119 does not honor; `ClaudeHookJsonAdapter`'s `Effect.Replace` arm. Re-probe on upgrade alongside the Stop check below. |
| ⚠ **The published docs disagree** | `code.claude.com/docs/en/hooks` documents Stop's decision control as a *nested* `hookSpecificOutput.permissionDecision`/`permissionDecisionReason`. No such member exists in 2.1.119. Either the docs run ahead of this release or they are wrong; the binary is what parses our stdout, so the binary wins. **Re-probe on upgrade:** `strings "$(readlink -f "$(which claude)")" \| grep -o 'hookEventName:E\.literal("[A-Za-z]*")' \| sort -u` — if `Stop` appears, the contract moved and the adapter branch must follow. | The deploy-time live check is the standing tripwire: `/deploy` exercises a real Stop, and a contract move shows up as a block that no longer blocks. |
